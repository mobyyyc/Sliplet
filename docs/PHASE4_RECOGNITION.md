## Intended everyday procedure

1. **Import one complete image.** Preserve its bytes and original evidence. Check orientation, boundary coverage and available resolution. Suggest adjusting the receipt outline only when needed. Perspective correction must be reversible to original coordinates, and must not trim a valid row or footer. An uncertain boundary falls back to the original full image.
2. **Read the whole receipt and understand its layout.** Use text and geometry to identify merchant/header, purchases, adjustments, printed summary and payment/footer regions. These are semantic areas, not three fixed horizontal slices. Merchant names may be logos; totals may appear above payment lines; discounts can occur within the item block.
3. **Assemble the complete draft.** Associate descriptions/SKUs with printed line amounts, distinguish unit price from line extension, preserve repeated identical purchases, join supported wrapped text, and recognize explicit quantities/weights, discounts, deposits and taxes. Populate merchant, date/currency when supported, subtotal and total. Preserve printed descriptions instead of inventing expanded product names.
4. **Reread uncertain evidence automatically.** A suspected item without an amount, unusually small text on a tall image or competing summary candidates can trigger a bounded regional pass. Compare resolution-preserving crops, overlapping strips and recognition alternatives in experiments first. The app uses only winning methods and a measured retry/time/memory budget, with cancellation and an unchanged baseline fallback.
5. **Ask the smallest useful question.** If uncertainty remains, open the relevant original region: adjust its boundary, select a source-backed candidate or edit the missing field. An optional “Highlight and reread” action accepts a region and, if useful, a purpose such as Items or Totals. Merchant → items → totals manual cropping is an advanced recovery option, not the normal import sequence. Unreadable or absent pixels require manual entry or a clearer image; repeated OCR cannot recover evidence that is not present.
6. **Review and save.** Show unresolved fields clearly. Fully automatic extraction means all visible, in-scope printed fields are correctly populated before assistance; it does not automatically grant the user's source-review confirmation. Finish/draft/split rules remain intact.

Arithmetic detects inconsistencies but never manufactures or selects an otherwise unsupported price/tax just to balance a receipt. Repeated OCR agreement is not independent ground truth. “Not printed”, “unreadable”, “not yet checked” and a verified printed zero must remain distinct.

## Human help and model work

**During development:** the user supplies complete images and verifies reference labels or ambiguous regions locally. Existing five checked receipts are enough to start. Ask only for unresolved annotations and later small batches of new purchases. Provisional labels remain provisional until checked. Region annotations are stored separately from the immutable originals and historical references. The assistant designs experiments, diagnoses aggregate failures, implements fixes and tests regression; private images/text/labels stay local and out of chat/public evidence.

**Inside the app:** Apple Vision and local receipt logic do automatic recognition. Apple Intelligence, a cloud vision service or this coding assistant is not a runtime dependency. Assistance uses source-backed alternatives and explicit edits. User corrections do not silently retrain an engine, rewrite ground truth, or become rules that memorize prices. A corrected receipt may become a development example only through explicit inclusion.

**When choosing technology:** keep the current engine as a control. If clearly legible text still cannot be recovered with measured regional methods, return with a separately scoped proposal to evaluate another bundled on-device OCR model. Compare accuracy, supported scripts, package size, license, runtime and device compatibility before adding a dependency. Do not repeat the failed document-recognition replacement without a specific new hypothesis.

## Diagnostic experiment before building the crop UI

For each relevant failure compare four paths:

- Current full-image app pipeline.
- The same pipeline with user-verified region boundaries supplied only as experimental input.
- Automatically proposed regions, without user hints.
- A checked text/geometry input supplied directly to interpretation, isolating parser errors from OCR errors.

This separates whether a field is unreadable, misread, grouped incorrectly, interpreted incorrectly or lost during conversion/storage. The manually marked-region result is assisted and cannot count as automatic accuracy. If manual regions work but automatic regions fail, improve segmentation. If checked text still fails, repair interpretation instead of asking the user for more crops. If readable pixels defeat every tested OCR path, evaluate the engine ceiling.

Score recovered raw transcription/evidence separately from complete parsed fields. A regional read can recover the correct text while the current parser still drops it; that is an evidence-recovery result, not yet an app-accuracy improvement. Such a variant can enter isolated integration work, but must pass the full end-to-end financial/regression gates before promotion.

Change one factor at a time: orientation/outline, resolution/overlap, candidate count, language configuration/correction and row association. Freeze original inputs and log engine/version/options privately. Check that merchant spelling aids never rewrite SKUs or financial digits. Crops, tiles and alternative candidates retain a transform to original coordinates and an attempt ID. Deduplicate by source location and reading evidence; equal descriptions/prices at different locations remain separate purchases. Keep all alternatives in evidence while selecting each printed observation at most once in the final interpretation.

## Evaluation design and practical gates

**Data:** start with the five existing purchases as development data. Expand in small batches toward roughly 30 distinct purchases if available, preferably balanced across the three stores; a practical eventual reservation is three untouched purchases per store. Reserve the test purchases before inspecting/tuning against them. Every alternate photo, crop and reimport of the same purchase belongs to the same split. Independent validation labels are user-checked locally and available to the evaluator, not to the implementation/candidate-selection path. After failures are used to tune, those purchases become development data; a new untouched set is needed for another independent claim. Few available new images do not block useful development, but limit the conclusions.

Include normal and difficult receipts: long item blocks, wrapped names, repeated prices/items, quantity/unit/weight lines, inline coupons, taxes/deposits, bilingual text and skew/fade. Artificial degradations are robustness checks, not new real purchases. Measure region-help usefulness on separately designated development cases before the final test.

**Automatic quality:** report merchant/date/currency and each printed summary field; purchase precision/recall and exact description-plus-line-amount matches; SKU, quantity/unit price/weight where present; adjustment kind/sign/amount/rate; omitted/extra/duplicate rows and confidently wrong values. Match repeated purchases one-to-one using verified identity/location rather than price alone. Full-receipt success requires every in-scope printed field and all lines correct before user actions. Unreadable and unlabelled references are explicitly counted, never silently dropped to improve the score.

**Assisted quality:** separately report complete receipts after assistance, unresolved receipts, number of crops/region adjustments/rereads/typed corrections and actual user review seconds. Annotating the reference set is development effort, not everyday correction time. Use matched receipt complexity and note order/practice effects when comparing review experiences.

**Targets:** full automatic population of every legible printed field is the product goal, not a guarantee that damaged photos yield perfect data. Retain at least 95% exact purchase-line recovery as an initial target; P4-01 must define precision, summary-field and full-receipt targets against the expanded field inventory before candidate development. Do not present 95% correct lines as 95% complete receipts. Promotion requires no new observed wrong financial values/duplicate rows, no regression on already correct development cases, and explicit per-store tradeoff review. A small untouched set can support a personal test decision, not a universal accuracy guarantee. Do not mark v0.4 accuracy goals achieved when only the original five are available.

**Runtime/compatibility:** measure cold/warm import-to-edit and regional retry latency, slow cases, peak memory, cancellation, background/lock cleanup and responsiveness on a fixed Simulator configuration. Choose the acceptable pass/latency budgets in P4-01 after baseline measurement. Source coordinate transformations, manual corrections, encrypted persistence/backup and app identity must survive the upgrade. No cloud requests, private-content logging or changes to the normal installed wallet during lab runs.
